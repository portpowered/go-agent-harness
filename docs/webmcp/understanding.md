# Verified understanding: WebMCP voice browser control

## Scope and verdict vocabulary

This document restates and audits `source-plan.md` against the repository as it exists on 2026-08-28. It does not validate the plan's external Chrome, `chromedp`, `cdproto`, WebMCP-specification, model, or showcase-site assertions; those are deliberately left as operator gates. “Ready” below means code can start against frozen local interfaces and fakes, “partial” means useful machinery exists but named gaps must be resolved, and “blocked” means a prerequisite is absent.

## 1. Intent and architecture in my own words

The product is a local bridge between one explicitly debug-enabled Chrome page and an existing `agent session`. Chrome supplies a changing, page-scoped catalog of WebMCP tools. A new `agent-cli` broker owns discovery, exact browser/tab selection, page generations, authorization, invocation correlation, cancellation, and cleanup. It exposes a small stable set of ordinary function tools (`webmcp_get_context`, tab/tool listing and selection, invoke, optionally cancel) to the model. OpenAI Realtime therefore never owns the CDP connection and does not treat the page as a remote MCP server.

The dependency direction is sound: browser concepts stay under a new `agent-cli/internal/webmcp` tree; only a raw JSON Schema capability belongs in the provider-neutral loop contract; provider packages only encode that contract. A repository-owned Chrome adapter should hide generated protocol types behind neutral `BrowserRuntime`/`TargetSession` interfaces. Fake discovery/session edges and semantic browser scripts prove most behavior; pinned Chrome proves only the adapter and external compatibility.

There are two integration gates. I1 proves explicit discovery, selection, catalog synchronization, invocation, structured output, and ownership-safe shutdown without a provider. I2 adds existing Realtime text/audio, multi-turn continuity, approval, barge-in policy, paired evidence, and state verification. The plan correctly treats rollback, arbitrary-profile takeover, projected dynamic tools, and two-agent use as non-MVP.

## 2. Verified mapping to current machinery

### Workspace and ownership

- The workspace currently includes only `agent-cli`, `go-agent-loop`, and `go-llm-gateway`, with local replacements from CLI to both libraries; helper/test modules are separate from the workspace (`go.work`, `test/localai/go.mod`, `tools/coveragegate/go.mod`, `tools/rtc-race-gate/go.mod`, `tools/session-race-gate/go.mod`, `tools/timingate/go.mod`).
- All of those manifests are still at Go 1.24.2, and `agent-cli` has no `chromedp`/`cdproto` dependency (`go.work`, `agent-cli/go.mod`, `go-agent-loop/go.mod`, `go-llm-gateway/go.mod`). Thus all browser packages, locks, launchers, and adapters in the plan are additions, not existing seams.
- The current root command has ask/chat/tool/interaction/probe/media/session/config/devices groups and no WebMCP route (`agent-cli/internal/cli/routes.go`). Browser ownership in `agent-cli` is therefore consistent with the real routing boundary.

### CLI capability and tool surface

- `agent tool` really is a direct, no-LLM path: it loads config, creates a config-filtered registry, parses scalar `key=value` arguments, and invokes by registered name (`agent-cli/internal/cli/tool.go`, `agent-cli/internal/tools/registry.go`). A separate `agent webmcp` group is justified because this registry is static and command-local.
- A CLI `Tool` exposes a JSON-Schema-shaped `Parameters() map[string]any`; `RegistryExecutor` parses a model call's JSON arguments and adapts tool messages into one correlated `ToolCallResponse` (`agent-cli/internal/tools/base.go`, `agent-cli/internal/tools/adapter.go`). Browser tools can implement this surface, but structured browser output must be deliberately serialized into the response string/envelope because `ToolCallResponse.Content` is textual (`agent-cli/internal/tools/adapter.go`, `go-agent-loop/pkg/messages/participant_messages.go`).
- Config layering is defaults, YAML, then `AGENT_` environment variables with `__` as nesting; flags are applied later by commands (`agent-cli/internal/config/loading.go`, `agent-cli/internal/config/overrides.go`). The proposed `AGENT_WEBMCP_*` spelling fits that loader, but the actual `Config` type has only `Model` and `Tools` today (`agent-cli/internal/config/interface.go`).

### Session capability construction and cleanup

- Session command construction already resolves an executor and definitions from the same loaded config snapshot, then passes both in `SessionRunOptions` (`agent-cli/internal/cli/session.go`, `agent-cli/internal/wire/composition.go`, `agent-cli/internal/services/session_options.go`). This is the right extension point for opt-in broker tools and preflight-before-provider-dial.
- The real `SessionToolCapabilities` has only `Executor` and `Definitions`; the plan's proposed `Close func() error` does not exist (`agent-cli/internal/cli/session.go`). Adding it is required, and every record/replay/audio/error exit must run it; current runtime cleanup is organized through `sessionRuntimePlan.run` and its provider/RTC cleanup paths (`agent-cli/internal/services/session_runtime_plan.go`).
- Production composition has named ports for tool executor, transport, inference, devices, audio, clock, and observation, but none for browser discovery/runtime/broker/policy/recording (`agent-cli/internal/wire/composition.go`). Wire constructors and generated output must both change (`agent-cli/internal/wire/wire.go`, `agent-cli/internal/wire/wire_gen.go`).
- The production factory creates a new config-filtered static registry for a session. It has no combined-executor or collision mechanism yet (`agent-cli/internal/wire/composition.go`, `agent-cli/internal/tools/registry.go`).

### Tool lifecycle, timeout, cancellation, and correlation

- The loop's tool contract carries provider call ID, name, and JSON-encoded arguments; results carry the original call ID (`go-agent-loop/pkg/messages/tool_values.go`, `go-agent-loop/pkg/messages/participant_messages.go`). `RegistryExecutor` and the session wrapper restore the provider's ID/name even when an inner executor is imperfect (`agent-cli/internal/tools/adapter.go`, `agent-cli/internal/services/session_tools.go`).
- The session wrapper converts tool errors, panics, cancellation, and a default 60-second deadline into nonfatal correlated tool results. It explicitly requires cooperative context cancellation; an executor that ignores context can continue in its goroutine after the session has moved on (`agent-cli/internal/services/session_tools.go`). WebMCP therefore needs its own invocation registry and bounded reconciliation, not merely this wrapper.
- A `ToolRunner` executes every call in one model batch concurrently and waits for all results in input order (`go-agent-loop/pkg/participants/tool_runner.go`). The broker must independently impose per-target FIFO/one-mutation-at-a-time policy.
- A control-plane interrupt cancels the current model and tool batch contexts and stales queued deltas (`go-agent-loop/pkg/subsystems/interrupt_handler.go`, `go-agent-loop/pkg/participants/tool_runner.go`). Separately, new audio while assistant audio is streaming sends provider `RESPONSE.CANCEL`, but it does not invoke the control-plane interrupt or a browser-specific cancel policy (`go-agent-loop/pkg/participants/model_runner.go`, `go-agent-loop/pkg/agentloop/agent_loop.go`). Lane J needs an explicit bridge among these paths.
- Duplex tool results are forwarded once by call ID to the provider-facing session (`go-agent-loop/pkg/subsystems/tool_result_forwarder.go`). Rejected sends and unresolved IDs are tracked by the CLI session observer (`agent-cli/internal/services/session_tool_lifecycle.go`, `agent-cli/internal/services/session_live.go`). These are reusable delivery/accounting seams, not a browser invocation state machine.

### JSON Schema and provider encoding

- The plan's schema blocker is real: `messages.ToolDefinition` contains only a flat `[]ToolParameter` (`go-agent-loop/pkg/messages/tool_values.go`); the CLI adapter discards nesting/enums/unions while flattening a root properties map (`agent-cli/internal/tools/adapter.go`); OpenAI chat and Realtime rebuild a shallow object schema (`go-llm-gateway/pkg/providers/openai/models.go`, `go-llm-gateway/pkg/providers/openai/session_config.go`).
- Adding `json.RawMessage` also requires owned-byte cloning in every snapshot/copy path, including the session inferencer and replay definition selection (`go-llm-gateway/pkg/inference/session_inferencer.go`, `agent-cli/internal/services/session_runtime_openai.go`).
- The shared-contract impact is broader than the plan says. Anthropic and Gemini also derive schemas exclusively from legacy `Parameters`; Grok serializes the shared definitions directly (`go-llm-gateway/pkg/providers/anthropic/models.go`, `go-llm-gateway/pkg/providers/gemini/models.go`, `go-llm-gateway/pkg/providers/grok/provider.go`). If the CLI adapter stops populating legacy parameters, those providers need raw-schema support or an explicit compatibility projection and regression tests.

### OpenAI Realtime voice integration

- OpenAI Realtime sessions, model/voice validation, text seeding, file/device audio, WebSocket/WebRTC selection, multi-turn waiting, and initial tool definitions already exist (`agent-cli/internal/services/session_models.go`, `agent-cli/internal/cli/session.go`, `agent-cli/internal/services/session_options.go`, `agent-cli/internal/services/session_audio_in.go`, `agent-cli/internal/services/session_audio_out.go`). Lane I is integration and lifecycle work, not a new voice stack.
- A bare live `agent session` is not currently admitted: the command prints help unless record, replay, recording-directory, or scheduled audio-turn input is selected (`agent-cli/internal/cli/session.go`). The plan's example with only `--webmcp` and device flags therefore requires `--webmcp` to become an explicit live-mode trigger, or it must include an existing capture mode.
- OpenAI translates inbound function-call start/delta/done events into loop tool events and serializes `function_call_output` with the original `call_id` (`go-llm-gateway/pkg/providers/openai/session_events.go`, `go-llm-gateway/pkg/providers/openai/session_messages.go`).
- The ordinary text tool-result encoder intentionally emits `conversation.item.create(function_call_output)` without `response.create`; the loop currently obtains continuation indirectly when the coordinator schedules follow-up inference and `ModelRunner` resends the latest user text, whose encoder adds `response.create`. Rich complete-message results use a different helper that can request the response directly (`go-llm-gateway/pkg/providers/openai/session_events.go`, `go-llm-gateway/pkg/providers/openai/session_messages.go`, `go-agent-loop/pkg/participants/model_runner.go`). The plan's simple “output, then request” sequence hides these two ownership paths; Lane E must preserve or deliberately replace them without duplicate user turns/responses.

### Recording and replay

- Provider session captures are versioned JSON envelopes of ordered client/server records, and strict replay validates outbound events structurally and reports divergence/incompletion/cancellation (`go-llm-gateway/pkg/testing/session_capture.go`, `go-llm-gateway/pkg/testing/session_replay.go`, `go-llm-gateway/pkg/testing/session_inferencer.go`). Tool-bearing OpenAI replay already conditionally reuses definitions when the recorded `session.update` contains tools (`agent-cli/internal/services/session_runtime_openai.go`).
- The CLI also has a complete recording-directory format with client/agent transcripts, session log, PCM segments, hashes, terminal summary, redaction, and `manifest.json` (`agent-cli/internal/services/session_recording.go`, `go-agent-loop/pkg/transcript/manifest.go`). The plan's proposed `provider.jsonl`/`transcript.jsonl` bundle is not the current layout; browser evidence should extend or reference the existing bundle rather than silently establish a second manifest contract.
- Browser semantic recording/replay is wholly new. Keeping it separate from provider wire capture, then pairing both through a manifest, matches the current separation of provider capture and transcript bundle (`go-llm-gateway/pkg/testing/session_capture.go`, `go-agent-loop/pkg/transcript/manifest.go`).

### Probe machinery

- The current neutral scenario loader is strict and supports only send text/audio/tool-result, advance, wait, and close steps plus its existing expectations (`go-agent-loop/pkg/probe/scenario.go`, `go-agent-loop/pkg/probe/expect.go`). Browser step/expectation additions belong here, while CLI execution/fixture derivation lives in `agent-cli/internal/cli/probe.go`.
- Acceptance already persists stdout/stderr/transcript/exit/report and a workspace snapshot before objective verification, and refuses unsupported or mismatched objective evidence (`agent-cli/internal/probe/acceptance.go`, `go-agent-loop/pkg/probe/acceptance.go`). This supports the plan's evidence-first principle.
- The plan's example scenario is not valid today: top-level `browser_fixture`, `provider_fixture`, and `expect` are rejected; the field is `expectations` (with limited aliases), and `send_audio` expects a corpus ID rather than a file path (`go-agent-loop/pkg/probe/scenario.go`). Lane K must version/extend the grammar and validators before using that example.

## 3. Discrepancies and missing prerequisites

1. “Implementation-ready” is conditional: O0/A are absent—Go remains 1.24.2, browser dependencies and all `test/webmcp`, `scripts/webmcp`, and `internal/webmcp` artifacts are not represented in the current module/router/config surfaces (`go.work`, `agent-cli/go.mod`, `agent-cli/internal/cli/routes.go`, `agent-cli/internal/config/interface.go`).
2. The plan accurately identifies schema flattening but understates blast radius across providers and clone/golden contracts (`agent-cli/internal/tools/adapter.go`, `go-llm-gateway/pkg/inference/session_inferencer.go`, `go-llm-gateway/pkg/providers/anthropic/models.go`, `go-llm-gateway/pkg/providers/gemini/models.go`).
3. The claim that existing session execution “handles cancellation” needs qualification: context cancellation and response cancellation exist, but browser protocol cancellation, mutation policy, late results, and non-cooperative workers do not (`agent-cli/internal/services/session_tools.go`, `go-agent-loop/pkg/participants/model_runner.go`, `go-agent-loop/pkg/subsystems/interrupt_handler.go`).
4. The source architecture oversimplifies continuation: the ordinary OpenAI encoder omits `response.create`, while `ModelRunner` later resends the latest user text to trigger it; rich results use a direct complete-message path (`go-llm-gateway/pkg/providers/openai/session_events.go`, `go-llm-gateway/pkg/providers/openai/session_messages.go`, `go-agent-loop/pkg/participants/model_runner.go`). WebMCP must retain exactly-one continuation semantics.
5. The proposed capability cleanup hook and browser composition ports are designs, not current machinery (`agent-cli/internal/cli/session.go`, `agent-cli/internal/wire/composition.go`).
6. The recording file names and probe example are stale relative to current public contracts (`go-agent-loop/pkg/transcript/manifest.go`, `go-agent-loop/pkg/probe/scenario.go`).
7. `agent-cli/internal/config/models.go` is the known-model registry; WebMCP configuration belongs primarily in the actual `Config` definitions/default loading in `agent-cli/internal/config/interface.go` and `agent-cli/internal/config/loading.go`.
8. The direct `agent tool` command cannot be reused as a persistent browser session by registration alone because it constructs a fresh static registry per invocation (`agent-cli/internal/cli/tool.go`, `agent-cli/internal/tools/registry.go`). Persisted selection plus reconnect semantics are required across separate `agent webmcp` commands.
9. The primary user-story command omits the capture/live admission flag that `agent session` currently requires; adding `--webmcp` flags alone will otherwise return help before runtime construction (`agent-cli/internal/cli/session.go`).

## 4. Risks and open questions

- Operator must prove the exact Go/chromedp/cdproto/Chrome pins, generated WebMCP surface, feature flags, and detach-only external-target lifecycle; the repository contains no local evidence for any of them (`go.work`, `agent-cli/go.mod`).
- Contract freeze must answer whether WebMCP retains the existing split continuation paths or introduces one owner, how multi-call batches request exactly one continuation, and how late browser results interact with the loop's exactly-once forwarder (`go-agent-loop/pkg/subsystems/tool_result_forwarder.go`, `go-agent-loop/pkg/participants/model_runner.go`, `go-llm-gateway/pkg/providers/openai/session_events.go`).
- Decide whether raw schema is authoritative for every provider or only supported ones, and how legacy projections fail on unions/nesting without silently weakening contracts (`go-agent-loop/pkg/messages/tool_values.go`, `go-llm-gateway/pkg/providers/anthropic/models.go`, `go-llm-gateway/pkg/providers/gemini/models.go`).
- Define one cleanup owner spanning capability, broker, target session, provider session, audio, and recording finalization; current capability values cannot close resources (`agent-cli/internal/cli/session.go`, `agent-cli/internal/services/session_runtime_plan.go`).
- Define the audio-to-browser interruption signal. Current automatic audio barge-in cancels assistant response only, while `SendInterrupt` is a separate API (`go-agent-loop/pkg/participants/model_runner.go`, `go-agent-loop/pkg/agentloop/agent_loop.go`).
- Approval needs a real interaction/state interface and deterministic test injection; none is present in current session capability construction (`agent-cli/internal/cli/session.go`, `agent-cli/internal/wire/composition.go`).
- Decide whether WebMCP authorizes a new uncaptured live-session mode or requires `--record-dir`; this affects the documented command, cleanup, and the requirement to retain evidence (`agent-cli/internal/cli/session.go`, `agent-cli/internal/services/session_recording.go`).
- Preserve current recording manifest compatibility and redaction guarantees when adding URLs, arguments, outputs, browser IDs, and paired files (`go-agent-loop/pkg/transcript/manifest.go`, `agent-cli/internal/services/session_recording.go`).
- Process discovery and persisted target selection are security-sensitive and platform-specific. Explicit endpoint/ID should remain the first supported path; current code supplies no browser precedent (`agent-cli/internal/config/interface.go`, `agent-cli/internal/cli/routes.go`).

## Bottom line

The architectural direction is compatible with the repository and should reuse the session, Realtime, replay, transcript, and acceptance foundations. It is not yet executable as parallel browser work until C0 resolves cleanup, raw-schema cross-provider behavior, Realtime continuation ownership, browser cancellation signaling, and fixture grammar, while O0/A independently prove the external toolchain and target-preservation assumptions. I1 is the correct cut line; I2 should adapt the existing voice vertical rather than rebuild it.
